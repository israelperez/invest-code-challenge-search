# Plan: Betashares instrument search POC
_Locked via grill — by Claude + Israel, 2026-10-25. Revised after Codex round 1._

Supporting docs (detail; this plan is the contract): [`docs/roadmap.md`](../roadmap.md), [`docs/walkthrough.md`](../walkthrough.md), [`docs/adr/`](../adr/) (0001 ID-first hydration, 0002 server-side search log, 0003 refinements apply on a button), [`CONTEXT.md`](../../CONTEXT.md), [`DESIGN.md`](../../DESIGN.md), [`ASSIGNMENT.md`](../../ASSIGNMENT.md), [`api/README.md`](../../api/README.md).

## Goal

Build a React search page on `http://localhost:3000` against the mock Search API in `api/` that meets every acceptance criterion in `ASSIGNMENT.md`, and goes further to demonstrate senior system design and frontend architecture: ID-first search with client-side hydration, a server-side search log powering popular searches and zero-result insights, and refinements that fetch results only when the user is ready. The submission is a public fork assessed by a hiring panel who will clone and run it. The architectural ambition is a deliberate choice by the candidate (to show backend-contract influence a senior frontend engineer would have); risk is controlled by building a runnable MVP milestone first and keeping every extra independently removable.

## Milestones

- **M1 — MVP vertical slice (meets every acceptance criterion):** API baseline tests, `/search/index` + `/instruments/batch`, search log + `/popular`, frontend foundation, layout, search bar + suggestions, popular pills, results + load more, filters + apply-on-button + sort + chips, loading/empty/error states, unit + component tests, one-command setup, README. Runnable and submittable on its own.
- **M2 — Extras (M2 UI removable without touching M1; the search log is an M1 primitive; insights is gated by `ENABLE_INSIGHTS`, each M2 panel/feature behind its own module and config flag):** recent searches, `/insights/zero-results` + Insights tab, Settings tab, Show raw data, console analytics, "Try removing" chips, header (Israel).
- **M3 — Theme (after M1/M2 work as wanted):** Chakra theme built from `DESIGN.md` (brand colours, Rund Text with Inter fallback, radii, focus ring). M1 and M2 are built and tested on Chakra's **default theme**; components use only semantic tokens and props (no hard-coded colours, fonts or radii), so M3 is theme config only, with no component edits.

## Approach

1. **API test harness + baseline.** Split `api/src/main.ts` into `createApp(deps): Koa` and a small bootstrap that listens. `deps` injects repository, search log, clock and config so tests get fresh in-memory state. Add Vitest + supertest and a `test` script. Characterise existing behaviour before any change, **including its quirks** (`from: 0` treated as page 1, unknown keys ignored, inclusive range bounds), so the legacy contract is pinned.
2. **Internal primitive.** Add `SearchService.searchAll(query)`: filter → rank → order over the full set, returning the ordered match list without pagination. Existing `search()` becomes `paginate(searchAll(query))`, which is behaviour-identical (proven by the baseline). New code only uses `searchAll`.
3. **`POST /search/index`** (new controller + service, strict validation, contract in [API contract](#api-contract)): one `searchAll` pass per request; facet counts for all 7 keys aggregated from that pass plus one pass per active facet (disjunctive counts), not one search per facet value. Facets start from the repository-wide value universe (every issuer and kind, every bucket from config, both boolean values) and overlay counts, so zero-count options are emitted explicitly. Ordering keeps the existing comparators (default order, text ranking, explicit `order_by`) and appends `symbol_openfigi` as the final comparator, in the index path only; legacy `search()` ordering is untouched. Returns `indexed_at` as a snapshot token.
4. **`POST /instruments/batch`** (contract below).
5. **Search log** (new module, injected) behind **`POST /searches { term, submission_id }` → 202**, a separate, tiny endpoint called on every **explicit** search submission (each user action is logged, even if superseded before its results render): a normal request that is never cancelled, but results never wait for it and failures only reach dev logs. Logging is decoupled from result retrieval so `/search/index` stays pure and cacheable. The server computes **`unfiltered_count`** itself (the count with no filters, memoised per **executable spelling**: trimmed, whitespace-collapsed, lowercased except `OR`, since dedupe can merge spellings that return different results), so the client never reports numbers and filter-induced zero results never count as a term failure. Non-empty dedupe key required. Records `{ key, spelling, client_id, unfiltered_count, submission_id }`. **Idempotent within a 10-minute retry window** on `submission_id` via a bounded registry (10,000 IDs, 10-minute TTL, oldest evicted first); a rate-limited submission is **not** recorded, so a later retry may be logged. `X-Client-Id` is **required** on `/searches`: missing or non-UUID → 400 (a client bug, logged in dev), distinct from silent rate-limit drops. Bounded: max 5,000 keys; per key, distinct clients counted up to 1,000 (saturating) and at most 10 spellings kept (least-frequent evicted first, oldest on ties), plus key-level `has_positive_result` and totals that survive spelling eviction, so a dropped variant can't turn a mixed key into a false zero-result insight. Eviction: lowest distinct-client count, then oldest last-seen. Seeded fake history on startup, clearly labelled as demo data in the UI and docs.
6. **`GET /popular`**: top N keys whose label spelling has `unfiltered_count > 0`, at least 3 distinct clients, no `OR` token, ranked by distinct clients then total; label = the most frequent spelling **that returns results** (a key with no positive spelling is never popular).
7. **`GET /insights/zero-results`** (M2): keys with `has_positive_result = false`, at least 2 distinct clients (reduces one-off noise; not anonymisation, since client IDs are spoofable — the panel carries a visible "development only" banner), grouped spellings with counts. Enabled only when the API runs with `ENABLE_INSIGHTS=true` (default true in the dev script); documented as admin-only in production.
8. **Dedupe key** (`dedupeKey(term)`): trim; split into clauses on whitespace-delimited uppercase `OR` (lowercase `or` is a word); malformed operators (leading, trailing, repeated) → not logged; in each clause lowercase, drop `and`, `the`, `of`, `for`, `asx`, keep `etf`, remove duplicate words, sort words; drop empty clauses; sort clauses; join with ` OR `. Empty key → not logged. Tests cover `OR`/`or`, repeated and leading/trailing operators, stop-word-only, blank, case and order variants.
9. **Security** (demo-grade, stated as such): strict schemas on new endpoints reject unknown fields, bound every number, whitelist `order_by` fields and directions, enforce ID format and ≤ 100 IDs, term length 1–100. Global body limit set explicitly to 32KB (legacy endpoints never need more). Rate limit on logging per IP and per client ID (token bucket); over the limit the search still succeeds but isn't logged. Client ID: random UUID in localStorage, sent as `X-Client-Id`, validated as a UUID, documented as spoofable (distinct-client ranking plus rate limits raise the cost of poisoning; real protection needs authenticated identity). CORS stays the existing global `cors()` (any origin): it's a local dev mock and CORS isn't a security boundary. `X-Client-Id` is allowed in preflight. Structured dev logs (no raw terms) for validation rejects, rate-limit drops and evictions.
10. **Frontend foundation.** Vite + React + TS in `web/` on 3000. Root scripts: `setup` (installs both), `dev` (a small Node script using built-in `child_process` to run API and web together, forwarding signals and cleaning up; no process-runner dependency), `test` (runs both suites), plus `web:install` / `web`. Typed `fetch` client. One canonical `buildSearchRequest(state)` (trimmed term, sorted filter keys and values, empty filters omitted) used for **both** the request body and the TanStack query key. Query keys also include `indexed_at` and every response-shaping value (`document_limit`, `id_limit`); a changed `indexed_at` in any response clears the document store and search caches. Restart discovery: a tiny `GET /version → { indexed_at }` query (60-second stale time, refetched on load, window focus and reconnect) invalidates everything when it changes, so a cache that never refetches still learns of a restarted API. `staleTime: Infinity` for search-index and document queries; `/popular` fetched once per load. `SearchSource` seam: index cache per state, `Map<id, Instrument>` store, hydration planner (pure: which IDs of the next batch are missing), next-window and batch fetches send the `snapshot` token. A 409 restarts atomically: the first batch reloads in place, focus moves to the results heading, and the live region announces "Results were refreshed". Chakra UI v3 on its default theme (custom theme is M3). `config.ts` with every tunable and a one-line description. State in React only. Pure logic in plain TS modules, thin components, DRY.
11. **Search vs refinement requests.** Every **search** submission sends `POST /searches` with a fresh `submission_id` (retries reuse it) and then reads results through the normal cached path, so a repeated search costs one tiny log request and no result request. Refinements, counts, hydration and the initial load never call `/searches`.
12. **Layout and shell.** Mobile-first: mobile 0–759px single column, filter drawer, `[Filters (n)]` + `[Sort]` row; tablet 760–1029px search across the top, 260px filter rail, results right; desktop 1030px+, max width 1030px centred. Full-width result rows. Sticky header by Israel.
13. **Search bar and suggestions.** Chakra Combobox (Ark UI, WAI-ARIA combobox pattern). Contract: Arrow Up/Down move through both groups, Home/End, Enter selects, Escape closes (second Escape clears), Tab closes and moves on, blur closes; groups labelled; `aria-activedescendant`; loading and "no suggestions" states announced through a polite live region. Suggestions from 3 chars, 200ms debounce, stale requests aborted. **Terms**: issuer values fetched once (`POST /facets/issuer` with `{}`), matched locally on the formatted label by word prefix (a small, bounded list; a real build swaps in `/suggest`). **Instruments**: top 5 via `/search?fields=symbol,symbol_openfigi,display_name,logo&size=5`. A search applies immediately, keeps applied filters and discards pending ticks.
14. **Popular pills.** Top 10 from `/popular`, labelled "Popular searches (demo data)" in the walkthrough and an info tooltip. Click = a search.
15. **Results.** Header ("31 results", sort select), applied-filter chips + "Clear filters", rows (logo with `onError` fallback to a default image and `referrerPolicy="no-referrer"`, ticker, name, type, issuer label, flag badges, units on issue). **Load more**: fixed-size button with inline spinner; appended skeleton rows; next batch appended atomically only when every requested document has arrived; the first new row gets `tabIndex={-1}` and is focused with `preventScroll`; a polite live region announces "15 more loaded, showing 30 of 834". IDs reported `missing` by the batch are skipped and logged to the console. Batch failure: rows stay, an inline error with Retry replaces the button. A new search or refinement cancels in-flight load-more. End-of-results message. Skeletons on a new search; friendly no-results; error with retry. Rows not clickable.
16. **Filters and ordering.** All 7 facets (Type, Issuer top 8 + "Show all" with filter box, Betashares only, Flagship, Auto Invest, Portfolio eligible only, Units on issue single-select buckets "Equities only"). AND across sections, OR within. **Count semantics (disjunctive):** an option's count is the number of results if that option alone were selected in its section, with every other section's pending selection applied (matches existing `FacetsService` semantics); truth-table tests pin it. Zero-count options are disabled **unless selected** (selected options always stay removable). **Apply on a button** everywhere: each tick sends a debounced (150ms) counts-only request keyed by the canonical pending state; responses for a superseded state are discarded (TanStack keys + abort), so counts never show a stale state. Button: "Show 1 result" / "Show 31 results" / disabled "No matching results", fixed width. Closing the drawer discards pending ticks. Sort in the results header, applied immediately, server-side. Chip × and "Clear filters" (filters only) apply immediately. Units buckets use the API's bucket edges as given; the inclusive-boundary overlap is an existing API behaviour, documented as a backend finding (no instrument currently sits on an edge; a test asserts that). Issuer label = display only via `issuerLabel(slug)` (casing override map, else title-case); slug is the value; never merged; colliding labels fall back to raw values.
17. **Extras (M2).** Recent searches (last 5, case-insensitive, removable, saved when the request fires, localStorage, in-memory updates). Console analytics `analytics.track()` (display only; `search_submitted`, `search_zero_results`, `suggestion_selected`). Gear panel: Insights tab, Settings tab (results per load, suggestion min chars, suggestion debounce, instrument suggestions, popular pills, recent kept, Show raw data; localStorage; reset). Show raw data via one `<RawHint>` (issuer, type, units, range buckets, instrument ID). "Try removing" chips on filtered zero results.
18. **Tests.** Everything runs with one `npm test`, assuming the reviewer has **no AI tooling and no browser test tooling**; no new dependencies beyond Vitest, Testing Library, jest-axe and supertest. API: baseline (step 1), new endpoints including every `include` combination, validation rejects, `/searches` idempotency and unfiltered-count attribution, bounds and eviction, dedupe cases (reordered `OR` clauses share a key; differently grouped words don't), spelling eviction preserving `has_positive_result`, superseded submissions still logged, rate limit, snapshot 409, batch edge cases, **CORS preflight** (`OPTIONS` with `Origin` and `Access-Control-Request-Headers: x-client-id`). Frontend unit: `buildSearchRequest`, hydration planner, recent store, wording, `issuerLabel`, config. **Contract integration** (in `web/tests/contract/`): a Vitest `globalSetup` starts the real API as a child process on a spare port using the API's own `ts-node` (no cross-package imports, no new dependency), and the frontend's real API client and `SearchSource` run against it over HTTP, catching request/response drift that mocked component tests can't. Frontend component (jsdom): combobox contract (step 13) with `jest-axe`, filter apply flow (tick → counts request, stale response ignored, no results until the button; fake timers for debounce/abort), load-more focus (`document.activeElement`) + live-region text + failure. Not automated, stated in the README: visual layout and real rendering across breakpoints, covered by the walkthrough's demo flows.
19. **Delivery.** Conventional Commits, atomic, tests with their code; branch + PR per workstream into the fork's `main`, no squash; Israel as author with the short AI trailer. `npm audit` clean. README (setup + how it works), walkthrough (condensed after review, then voice-checked), roadmap, ADRs, "How I used AI".

## API contract

```ts
// POST /search/index
type SearchIndexRequest = {
  search_text?: string;                    // 0–100 chars; empty = browse
  kind?: string[]; issuer?: string[];      // same filter shapes as /search
  is_betashares?: { value: boolean }; is_flagship_fund?: { value: boolean };
  is_portfolio_excluded?: { value: boolean }; is_auto_invest_included?: { value: boolean };
  units_circulating?: { min?: string; max?: string };
  order_by?: `${"symbol" | "display_name" | "units_circulating"}.${"asc" | "desc"}`; // omitted = API default order
  include?: Array<"count" | "facets" | "ids" | "documents">; // default all; deduplicated
  id_offset?: number;                      // default 0, ≥ 0
  id_limit?: number;                       // default 1000, 1–1000
  document_limit?: number;                 // default 15, 0–100; documents.length = min(document_limit, ids.length)
  snapshot?: number;                       // indexed_at from the first response; required when id_offset > 0
};                                         // unknown fields → 400. Header X-Client-Id: UUID (optional).

type FacetValue = { value: string; count: number };
type SearchIndexResponse = {
  indexed_at: number;                      // always present
  count?: number;                          // when "count" included
  facets?: Record<"kind" | "issuer" | "is_betashares" | "is_flagship_fund"
    | "is_portfolio_excluded" | "is_auto_invest_included" | "units_circulating", FacetValue[]>;
  ids?: string[];                          // when "ids" included: ordered window
  next_id_offset?: number | null;          // when "ids" included: null = no more
  documents?: InstrumentDocument[];        // when "documents" included; requires "ids" (else 400)
};
// 409 { message, indexed_at } when snapshot ≠ current indexed_at.
// include rules: "documents" without "ids" → 400. When "ids" is excluded, id_offset / id_limit / document_limit are ignored.
// An id_offset past the end returns ids: [], next_id_offset: null. Counts-only = include ["count","facets"].
// GET /version → { indexed_at }

// POST /instruments/batch
type BatchRequest = { ids: string[]; snapshot: number }; // 1–100 IDs; canonicalised to uppercase then matched (consistent with existing case-insensitive lookup); format /^[A-Z0-9.]+:[A-Z]{2}$/; duplicates collapsed; 409 on snapshot mismatch
type BatchResponse = { documents: InstrumentDocument[]; missing: string[]; indexed_at: number }; // both in request order

// POST /searches                 { term: string (1–100 chars), submission_id: UUID } + X-Client-Id header
//                                  → 202 (also 202 when rate-limited or empty key: not logged, never an error to the user)
// GET /popular?limit=10           → { terms: { label: string; key: string; clients: number }[], includes_seed_data: true }
// GET /insights/zero-results      → { groups: { key: string; clients: number; total: number;
//                                      spellings: { text: string; total: number }[] }[], includes_seed_data: true }
```

Examples (full, counts-only, continuation) are added to `api/README.md` with the endpoints.

## Key decisions & tradeoffs

- **ID-first hydration over server-paged documents** — the candidate's deliberate showcase. Costs: two endpoints, client hydration logic, a second request for later batches. Gains: one store per instrument, no duplicate downloads, ready for live prices and more markets. Byte savings are modest at 834 records; the case is future shape, stated plainly.
- **Extending the mock API** although the brief says "build against" it (its README permits changes). Additive only; legacy behaviour pinned by baseline tests; `search()` refactored onto `searchAll` with identical output.
- **ID window 1,000 + snapshot token** over a hard cap or unbounded IDs.
- **Counts-only requests while ticking** over client-side counts (wrong once windowed) or no counts until applied (no live total).
- **Apply-on-button on desktop too**: one extra click vs fewer requests and no churn. Codex suggested live-apply; kept as the user's decision.
- **Server-side search log** with `unfiltered_count`, idempotent `submission_id`, bounded aggregates, distinct-client ranking. Demo-grade abuse resistance, stated as such.
- **Logging separated from retrieval** (`POST /searches`): keeps the result cache for repeats while every submission is still logged; counts stay server-computed.
- **Search vs Refinement** for popular, recent and analytics.
- **Frontend displays data as given**; data-quality findings (look-alike slugs, shared logos, missing display names, overlapping unit buckets) go to the backend.
- **Load more** over numbered pages; **React state** over URL state (Codex raised refresh/share; kept as the user's decision, rationale documented in the walkthrough).
- **All 7 filters**, **insights**, **settings**: kept as the user's decisions; insights and settings are M2 and removable.
- **Accessibility over brand-exact colour**.

## Risks / open questions

- **No browser E2E suite — explored and rejected.** Both Codex reviewers flagged cross-boundary risk. Playwright was considered: its browser downloads add hundreds of MB for one flow, and reviewers can't be assumed to have browser tooling or AI. The specific risks are covered inside `npm test` instead: in-process contract integration tests (contract drift, timing), supertest preflight (CORS), jsdom focus and live-region assertions. Remaining gap: visual layout, covered manually by the demo flows.
- **Rund Text hotlinked from onlinewebfonts (user decision, final).** Non-commercial POC for Betashares, who use the font on their own site. Residual risk: the host's licence and availability are unverified (Betashares' licence covers their site, not this host). Mitigation: `font-display: swap`, Inter fallback, files never committed.
- Scope is large for a challenge; M1/M2 split means M2 can be cut without unravelling M1.
- `searchAll` refactor touches an existing service; baseline tests are the guard.

## Out of scope

Real analytics pipeline; admin auth on insights; authenticated client identity; did-you-mean / synonyms; instrument detail page; prices, performance, fees, price sort, live prices; syncing recent searches to an account; persisting the search log across restarts; cleaning issuer data or fixing unit-bucket edges at source; changing existing endpoints' behaviour.
